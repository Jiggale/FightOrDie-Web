# 燃薪者 V0：燃烧生存核心设计

> 状态：等待用户审核  
> 日期：2026-11-05  
> 本设计只覆盖 V0 的第一阶段：验证燃烧、战斗消耗和余烬奖励。剧情分支、非致命路线与契灵承诺在后续切片中实现。

## 1. 目标

证明玩家能够在一场战斗中直接理解以下关系：

- 行动会推进燃烧倒计时；
- 战斗胜利会获得余烬；
- 战斗拖得越久，生存成本越高；
- 获得余烬仍然不等于安全；
- 当前状态能明确显示“还能行动几次”和“胜利后获得多少”。

本阶段不做完整剧情，不做长期存档，不做完整契灵系统。

## 2. 非目标

- 不实现遗物调查。
- 不实现技能树、装备掉落和新道具。
- 不实现多章节、多敌人或最终 Boss。
- 不实现契灵承诺的长期后果。
- 不接入 Inky/ink；叙事接入属于后续任务。
- 不把角色、余烬或燃烧状态持久化到数据库。
- 不重做整体视觉风格和页面结构。

## 3. 玩家体验

玩家进入一场专门用于验证系统的战斗：

1. 初始燃烧为 `5/6`，余烬为 `0`。
2. 每次完整战斗回合结束后，燃烧减少 `1`。
3. 玩家具有当前默认属性：HP 100、攻击 10、防御 5。
4. 敌人为“夺烬者”：HP 24、攻击 4、防御 2。
5. 按普通攻击计算，通常需要三个回合击败敌人。
6. 胜利后获得 `5` 点余烬。
7. 界面同时显示燃烧、余烬、战斗回合和胜利奖励预测。
8. 如果燃烧在战斗结束前归零，玩家立即失败，伤害与敌人状态不再继续处理。

这套数值只用于 V0 验证，不视为最终平衡值。

## 4. 回合规则

一个完整回合严格按以下顺序执行：

1. 玩家选择一个行动。
2. 结算玩家行动。
3. 如果敌人未死亡，敌人执行一次行动。
4. 无论敌人或玩家是否死亡，本回合都算完成，燃烧减少 `1`。
5. 先判断燃烧是否归零；归零时结局为“燃尽”，不发放任何战斗奖励。
6. 燃烧未归零且敌人死亡时，结算为胜利并发放奖励。
7. 燃烧未归零且玩家死亡时，结算为普通战败，不发放奖励。
8. 已经结束的会话不再接受行动，也不再扣燃烧。

现有战斗策略和 AI 策略不得重复造成同一次敌人攻击。每个完整回合只能出现一次敌人行动。

## 5. 状态模型

新增一个独立燃烧状态，至少包含：

| 字段 | 含义 |
|---|---|
| `flame` | 当前燃烧值 |
| `maxFlame` | 当前燃烧上限 |
| `ember` | 持有的余烬 |
| `burnPerTurn` | 每个完整战斗回合消耗的燃烧值 |

初始值为：

```text
flame = 5
maxFlame = 6
ember = 0
burnPerTurn = 1
```

状态只能在本场战斗会话内保存，不要求跨会话持久化。

## 6. API 合同

开始战斗时返回：

```json
{
  "sessionId": "abc12345",
  "battleOutcome": "ONGOING",
  "player": {
    "name": "hero",
    "level": 1,
    "health": 100,
    "maxHealth": 100,
    "attack": 10,
    "defense": 5,
    "gold": 0,
    "exp": 0
  },
  "monster": {
    "name": "夺烬者",
    "level": 1,
    "health": 24,
    "attack": 4,
    "defense": 2,
    "aiType": "AGGRESSIVE"
  },
  "strategies": {
    "1": "普通攻击",
    "2": "防御",
    "3": "治疗（恢复30HP）"
  },
  "burning": {
    "flame": 5,
    "maxFlame": 6,
    "ember": 0,
    "burnPerTurn": 1
  }
}
```

执行行动、查询状态和逃跑时返回同一结构，并额外包含：

```json
{
  "combatEnded": false,
  "playerWon": false,
  "battleOutcome": "ONGOING",
  "log": ["本回合日志"],
  "turn": 1
}
```

`playerWon` 只有在燃烧未归零且敌人死亡时为 `true`。现有前端读取字段 `log`，后端必须返回同名数组，不得返回前端无法读取的 `messages` 字段。

### 战斗结局

后端使用单一结局枚举，前端不得根据几个布尔值自行猜测结局：

| 值 | 含义 |
|---|---|
| `ONGOING` | 战斗尚未结束 |
| `VICTORY` | 玩家胜利 |
| `DEFEATED` | 玩家被敌人击败 |
| `EXTINGUISHED` | 燃烧归零 |
| `FLED` | 玩家成功逃跑 |

结局判定优先级固定为：

```text
燃烧归零 → 敌人死亡 → 玩家死亡 → 逃跑成功 → 继续战斗
```

开始战斗时返回 `ONGOING`。成功逃跑必须返回 `FLED`，不能和普通战败共用表现。

逃跑接口也必须返回完整的战斗状态，不能返回字符串。每次逃跑尝试消耗 `1` 燃烧。失败时战斗继续，并把“逃跑失败”和燃烧消耗写入 `log`；成功或燃尽时结束战斗。

## 7. 胜利结算

- 只有在玩家获胜时发放余烬。
- 每次战斗最多发放一次胜利余烬。
- 本阶段固定奖励为 `5` 余烬。
- 失败或逃跑不发放余烬。
- 已经结束的会话再次执行行动不得重复扣燃烧或重复奖励。
- 经验、金币和击杀记录与余烬使用同一胜利结算入口，避免燃烧失败时提前发奖。
- 胜利结算方法必须自行检查“敌人已死亡、玩家未燃尽、奖励未发放”，不能只依赖调用方保证。

## 8. 前端表现

战斗页新增一条燃烧信息：

```text
燃烧 5/6 · 每回合 -1 · 余烬 0
```

战斗中实时更新。达到 1 或更低时使用已有主题中的高风险强调；不使用硬编码色值。

战斗结算弹窗显示：

```text
获得余烬 +5
当前燃烧 2/6
```

如果因燃烧归零失败，标题为“燃尽”，不能显示为普通战败。

## 9. 数据结构与边界

建议职责划分：

- `BurningState`：只管理燃烧数值、余烬增加和回合消耗。
- `GameSession`：持有燃烧状态、战斗日志，并保证奖励幂等。
- `BattleService`：在战斗流程正确的位置调用回合消耗和胜利奖励。
- `BattleController`：只负责 API 映射，不写规则。
- 前端 store：接收并保存燃烧状态，不自行计算业务结果。

## 10. 验收标准

- [ ] 新战斗开始时显示燃烧 `5/6`、余烬 `0`、每回合消耗 `1`。
- [ ] 执行一个完整回合后燃烧恰好减少 `1`。
- [ ] 一次玩家行动不会触发两次敌人攻击。
- [ ] 战斗胜利后余烬恰好增加 `5`。
- [ ] 同一个已结束会话不会重复获得胜利余烬。
- [ ] 燃烧归零会结束战斗并显示“燃尽”。
- [ ] 胜利及燃烧归零发生在同一回合时，“燃尽”优先，不发放余烬。
- [ ] 成功逃跑返回 `FLED` 并显示“已撤退”，不会显示为普通战败。
- [ ] 开始战斗时前端立即显示玩家 HP、攻击和防御，不等待第一次行动。
- [ ] 开始、行动、查询和逃跑接口都返回结构一致的 `log` 与 `burning`。
- [ ] 后端单元测试覆盖燃烧扣减、下限、奖励幂等和燃尽结局。
- [ ] 前端能够显示并实时更新燃烧与余烬。
- [ ] 完成一次从开始战斗到胜利结算的手动复现。
